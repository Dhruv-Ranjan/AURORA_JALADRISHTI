# AURORA-JALADRISHTI

Integrated satellite intelligence for drought monitoring, spectral
reconstruction, and resource-aware mission planning.

[![Python](https://img.shields.io/badge/Python-3.11%2B-3776AB?logo=python&logoColor=white)](https://www.python.org/)
[![PyTorch](https://img.shields.io/badge/PyTorch-2.8%2B-EE4C2C?logo=pytorch&logoColor=white)](https://pytorch.org/)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

> **NASA Space Apps project:** AURORA reconstructs missing spectral bands from
> RGB observations, forecasts drought risk across time, and gives a mission
> planner a resource-aware observation target.

## What this project does

AURORA-Jaladrishti is an end-to-end research prototype with three connected
parts:

1. **Spectral reconstruction** — `SpectralNetV10` maps RGB inputs to six-band
   spectral targets.
2. **Drought forecasting** — a physics-guided temporal model combines
   reconstructed observations and sequence features to estimate drought risk.
3. **Mission planning** — the AURORA planner ranks candidate observations by
   expected information gain per resource cost, accounts for battery/storage
   constraints, and performs a simulated belief update.

The planner is not a neural model. It consumes drought forecast outputs from
the learned components and turns them into an observation decision.

## Results from the verified production run

The selected production run was trained from the stronger balanced
`SpectralNetV10` baseline. The massive-data pretraining experiment is retained
as an ablation because it reduced downstream performance.

| Metric | Verified result |
|---|---:|
| Spectral reconstruction RMSE | 0.02523 |
| Drought validation accuracy | 0.9373 |
| Drought validation precision | 0.8933 |
| Drought validation recall | 0.9784 |
| Drought validation F1 | 0.9339 |
| Drought validation AUC | 0.9526 |
| Integrated end-to-end drought F1 | 0.9324 |

These are research results, not operational drought alerts. The validation
split is not geographically disjoint and the drought targets are
predominantly proxy-derived. See the limitations section before interpreting
the numbers.

## Quick start on Windows

### 1. Create an environment

From PowerShell:

```powershell
cd G:\CubeSat\FINAL_PROJECT_NASA
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r .\requirements.txt
```

PyTorch installation can vary by CPU/GPU and operating system. If the
requirements installation cannot select the correct PyTorch wheel, install
PyTorch using the command generated by the official
[PyTorch selector](https://pytorch.org/get-started/locally/), then install the
remaining requirements.

### 2. Restore local inputs

Before running, place the verified local tensors and checkpoints in the paths
expected by the scripts:

```text
data\dataset_seq_forecast_production_real.npz
artifacts\spectral_v10_1_balanced.pt       # optional warm-start checkpoint
```

The public repository does not contain these large files. Do not treat the
29,487-row metadata manifest as 29,487 training samples: it contains scene
metadata, not RGB pixels or spectral targets.

### 3. Run the production pipeline

```powershell
.\.venv\Scripts\python.exe .\run_project.py
```

The runner trains the local models, evaluates reconstruction and drought
metrics, checks regional inference, and passes predictions through the AURORA
mission planner. Results are written to `artifacts\`.

To run a smaller smoke test:

```powershell
$env:SPECTRAL_EPOCHS="1"
$env:DROUGHT_EPOCHS="1"
.\.venv\Scripts\python.exe .\run_project.py
```

Use the full production settings for reported results. Smoke-test metrics are
only for checking that the pipeline is wired correctly.

## Massive-data workflow

The remote workflow first materializes and validates Sentinel-2 patches, then
trains spectral reconstruction. It does not invent drought labels from
metadata:

```powershell
.\.venv\Scripts\python.exe .\src\materialize_manifest.py `
  --manifest .\data\aurora_100k_resigned_samples.jsonl `
  --output .\data\massive_10000_rgb_spec.npz `
  --limit 10000 `
  --cache .\.remote_cache

$env:MASSIVE_DATASET="$PWD\data\massive_10000_rgb_spec.npz"
.\.venv\Scripts\python.exe .\src\train_massive_spectral.py
```

Or run the wrapper:

```powershell
.\run_massive_project.ps1
```

The `10,000` value is a candidate limit, not a guaranteed sample count. In
the verified run, 978 patches survived retrieval and quality checks. Network
access, signed URLs, scene availability, geographic bounds, and pixel quality
can all reduce the materialized count.

## Scientific limitations

- The current validation split is not a strict geographic holdout.
- Drought supervision is largely proxy-derived rather than direct field
  measurements.
- The remote metadata manifest is not itself a tensor dataset.
- The mission planner uses simulated resource and belief-update behavior.
- Results depend on the exact local data, preprocessing, random seeds, and
  dependency versions.
- The system is a research prototype and must not be used as the sole basis
  for agricultural, emergency, or policy decisions.
